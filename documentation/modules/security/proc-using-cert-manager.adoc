= (Early Access) Configuring your Kafka cluster to use cert-manager

[role="_abstract"]
Perform the steps in this procedure to enable cert-manager to issue certificates on either a new or existing cluster.

.Prerequisites

* cert-manager is installed in the cluster with a ready `Issuer` or `ClusterIssuer` configured with a Secret that contains a certificate and key pair for the CA. The Secret must have `tls.crt` and `tls.key` keys, where `tls.crt` is the CA certificate. You provide this certificate to the Cluster Operator as `ca.crt` in a Secret in the following step.

[NOTE]
====
When a Kafka component is removed, Strimzi cleans up the associated `Certificate` resources, but by default cert-manager does not delete the corresponding `Secret`.
Those Secrets are left behind and must be removed manually.
To have cert-manager automatically delete Secrets when their `Certificate` is deleted, install cert-manager with the `--enable-certificate-owner-ref` flag enabled.
See link:https://cert-manager.io/docs/usage/certificate/#cleaning-up-secrets-when-certificates-are-deleted[Cleaning up Secrets when Certificates are deleted] in the cert-manager documentation.
====

.Procedure

. Create a `Secret` containing the CA certificate that the Cluster Operator should trust.
+
[source,shell,subs="+quotes"]
----
kubectl create secret generic _<ca_cert_secret_name>_ \
  --from-file=ca.crt=_<path_to_ca_cert_pem>_ \
  -n _<namespace>_
----
+
Replace _<ca_cert_secret_name>_ with a name of your choice, _<path_to_ca_cert_pem>_ with the path to the CA certificate PEM file, and _<namespace>_ with the namespace of the Kafka cluster.
+
TIP: To automate provisioning and renewal of this Secret, you can use https://cert-manager.io/docs/trust/trust-manager/[trust-manager] to copy the `ca.crt` from the issuer's Secret into a separate Secret for the Cluster Operator.

[NOTE]
====
The `ca.crt` file in the Secret must contain either a single CA certificate or a CA certificate chain that can be used to trust certificates issued by cert-manager.
If providing a CA certificate chain, any intermediate CAs should be provided first, in order, with the root CA being the last certificate.
A cert-manager `SelfSigned` issuer type cannot be used directly because it does not provide a CA certificate.
====

. Create or update the `Kafka` resource, setting `type: cert-manager` on `clusterCa`, `clientsCa`, or both.
Set `generateCertificateAuthority: false` and provide the `certManager` configuration.
+
.Example `Kafka` resource using cert-manager for both Cluster CA and Clients CA
[source,yaml,subs="attributes+"]
----
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: my-cluster
spec:
  clusterCa:
    generateCertificateAuthority: false <1>
    type: cert-manager <2>
    certManager:
      issuerRef:
        name: my-cluster-ca-issuer <3>
        kind: ClusterIssuer <4>
        group: cert-manager.io <5>
      caCertRef:
        secretName: _<cluster_ca_cert_secret_name>_ <6>
        certificate: ca.crt <7>
  clientsCa:
    generateCertificateAuthority: false
    type: cert-manager
    certManager:
      issuerRef:
        name: my-clients-ca-issuer <8>
        kind: ClusterIssuer
        group: cert-manager.io
      caCertRef:
        secretName: _<clients_ca_cert_secret_name>_ <9>
        certificate: ca.crt
  kafka:
    # ...
  # ...
----
<1> Required. Must be `false` when `type` is `cert-manager`.
<2> Enables cert-manager certificate issuance for this CA role.
<3> Name of the cert-manager `Issuer` or `ClusterIssuer` to use.
<4> Kind of the issuer. Must be `Issuer` or `ClusterIssuer`.
<5> API group of the issuer. Defaults to `cert-manager.io`.
<6> Name of the `Secret` containing the CA certificate.
<7> Key within the `Secret` that holds the CA certificate PEM data.
<8> Required by the API schema but not used by the operator to issue certificates. You are responsible for issuing client certificates using cert-manager (see step 4).
<9> Name of the `Secret` containing the clients CA certificate. The Cluster Operator adds this certificate to the Kafka truststore.

. Apply the `Kafka` resource.
+
[source,shell,subs="+quotes"]
kubectl apply -f _<kafka_resource_file>_ -n _<namespace>_

. Verify that cert-manager `Certificate` resources have been created for each Kafka component.
+
[source,shell,subs="+quotes"]
kubectl get certificates -n _<namespace>_

When performing this procedure on an existing cluster, the Cluster Operator detects the change and initiates a multiphased rolling restart of all components to switch to the new CA type.

. To use mTLS authentication with client certificates issued by cert-manager, create a `KafkaUser` with `spec.authentication.type: tls-external`.
+
.Example `KafkaUser` with `tls-external` authentication
[source,yaml,subs="attributes+"]
----
apiVersion: kafka.strimzi.io/v1
kind: KafkaUser
metadata:
  name: my-user
  labels:
    strimzi.io/cluster: my-cluster
spec:
  authentication:
    type: tls-external
  authorization:
    # ...
----
+
[source,shell,subs="+quotes"]
kubectl apply -f _<kafka_user_file>_ -n _<namespace>_

. Create a cert-manager `Certificate` resource for the client certificate.
+
.Example cert-manager `Certificate` for the KafkaUser
[source,yaml,subs="attributes+"]
----
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-user
  namespace: kafka
spec:
  commonName: my-user # <1>
  duration: 2160h
  isCA: false
  issuerRef:
    group: cert-manager.io
    kind: ClusterIssuer
    name: my-ca-issuer # <2>
  privateKey:
    algorithm: RSA
    encoding: PKCS8
    size: 4096
  renewBefore: 360h
  secretName: my-user
----
<1> The `commonName` must match the name of the `KafkaUser` resource. Kafka uses the CN from the client certificate as the principal for authentication and authorization.
<2> The issuer must be backed by the same CA whose certificate is provided in `clientsCa.certManager.caCertRef`, so that the issued certificate is trusted by the Kafka cluster.
+
[source,shell,subs="+quotes"]
kubectl apply -f _<certificate_file>_ -n _<namespace>_
